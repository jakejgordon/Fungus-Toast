## 1. Vocabulary

- **Strategy:** A stable, named plan that combines reusable decision policies,
  parameters, complementary Adaptations, authored intent, and catalog metadata.
- **Controller:** The single Core entry point that receives a decision request,
  constructs explicit context, calls the appropriate policy, validates the
  result, and records a trace.
- **Policy:** A reusable typed decision component, such as mutation acquisition,
  surge activation, or mycovariant selection.
- **Candidate:** A generated, fingerprinted strategy definition being evaluated.
  It is not player-facing merely because it passes into the testing catalog.
- **Condition:** One fully resolved combination of lineup, board, player count,
  position assignment, enabled systems, loadouts, and seed schedule.
- **Calibration:** Evaluation on the visible reference corpus used for iteration
  and threshold construction.
- **Holdout:** Evaluation on frozen conditions excluded from candidate tuning.
- **Promotion:** Moving a passing candidate from the generated testing catalog
  into a reviewed campaign or single-player pool.
- **Performance band:** A versioned empirical classification derived from
  normalized outcomes, uncertainty, and robustness under named conditions.
- **Teaching mistake:** An explicit, intentional strategic weakness used by a
  Training opponent. It is authored metadata/behavior, not an accidental bad
  parameter or an undocumented handicap.
- **Scenario control:** A non-intelligence input such as position, map geometry,
  granted Adaptations, nutrient patches, or draft availability.

## 2. Standard Identity Contract

The name reset will use separate machine and human identities:

- `StrategyId`: `ai.<primary-archetype>.<identity>.v<major>`
- `DisplayName`: short unique player-safe name
- `IntentSummary`: one or two player-safe sentences describing opening,
  transition, win condition, and material weakness
- structured primary/secondary archetypes
- optional explicit `TeachingMistake`
- ranked complementary Adaptation options
- policy configuration and behavior fingerprint
- authored lifecycle/role metadata
- measured performance metadata kept outside the immutable ID

Difficulty, pool membership, lifecycle, and current measured strength must not
appear in the stable ID because recalibration can change them. Generated
candidates use a candidate namespace and receive a stable `ai.*` ID only on
promotion.

## 6. `ParameterizedSpendingStrategy` Precedence and Coupling

### Public constructor controls

1. name
2. high-tier preference
3. priority mutation categories
4. maximum tier
5. ordered target goals
6. surge-priority IDs
7. surge-attempt frequency
8. economy bias
9. structured mycovariant preferences
10. legacy preferred-mycovariant IDs
11. excluded mutation IDs
12. starting-spore edge offset

### Fixed rules hidden behind those controls

- fixed Early/Mid/Late round boundaries
- automatic early-game priority for three economy mutations
- recursive prerequisite selection, including ANY and category-investment gates
- a hard-coded expensive-prerequisite banking threshold
- scheduled surge activation before normal fallback
- last-place catch-up surge activation based on mutation tags
- a fixed two-round lookahead for surge banking
- fallback category shuffle, then global fallback, then economy-weighted random
- a final burn-off of leftover points
- a second last-resort surge attempt
- Tendril board scoring and an orthogonal-growth guard
- a mycovariant always-pick score threshold before authored preference

### Authoring consequences

- `economyBias` is not a global economy plan; it primarily weights late fallback
  while the fixed early economy pass applies independently.
- `priorityMutationCategories` does not control the target-goal spine and is
  shuffled rather than expressing stable priority order.
- surge behavior is split across goal acquisition, scheduled activation,
  catch-up activation, banking, and last-resort activation.
- starting position and mycovariant choice are coupled into a class whose public
  interface promises mutation spending only.
- candidate generation cannot safely treat constructor parameters as independent
  genes because fixed logic and precedence create interactions not expressed in
  the definition.

This supports the composed-controller hypothesis, subject to the Phase 4 bakeoff.

## 7. Invocation Ownership and Determinism Audit

### Simulation

- `GameSimulator` creates one `Random(seed)` and routes it through turn phases,
  draft execution, placement, and most gameplay effects.
- `MatchupRunner` derives per-game seeds and rotates strategy assignment when
  requested.
- Simulation invokes AI spending once per mutation phase through
  `TurnEngine.AssignMutationPoints`.

### Unity

- `GameManager.StartNextRound` calls `MutationPointService.AssignMutationPoints`.
- That service calls `TurnEngine.AssignMutationPoints`, which assigns points and
  immediately invokes every player's strategy.
- After humans finish, `GameManager` calls
  `MutationPointService.SpendAllMutationPointsForAIPlayers`, which invokes AI
  strategies again in the same mutation phase.
- The first Unity call constructs `new System.Random()` instead of using the
  `GameManager` random source; the second uses `GameManager.GetRng()`.
- Fast-forward uses `TurnEngine.AssignMutationPoints` with the GameManager RNG
  and therefore follows the Simulation one-call shape.

This is a **critical characterization item**. It may allow a Unity AI to revisit
banking or spending twice per round and makes normal Unity behavior differ from
Simulation/fast-forward. It must be proven with focused tests or a Unity-side
trace before ownership is changed; the audit itself does not alter behavior.

### Additional nondeterministic seams

- Resolved during Phase 2 hardening:
  `RandomMutationSpendingStrategy` now routes its passed RNG through
  `MutationSpendingHelper.TrySpendRandomly`, and the unused unseeded static RNG
  was removed from `MutationSpendingStrategyBase`. A regression test proves
  matching seeds produce matching portfolios and a different seed changes the
  result.
- `MycovariantEffectProcessor.OnResistantCellPlaced` constructs `new Random()`
  for Hyphal Resistance Transfer, preventing replay equality when that effect is
  active.
- Some roster sampling falls back to `Random.Shared` or `new Random()` when no
  seed is supplied. Resolved manifests must always supply explicit streams.

Replay equality cannot be claimed until these seams are either routed through
the explicit random source or excluded from the condition with a declared reason.

### Gaps for strategy performance bands

- parity-normalized final board share is not computed
- total living cells per game and tie-aware final rank are not first-class rows
- win-rate surplus versus `1 / player_count` is not computed
- no strategy-level interval/uncertainty calculation for primary outcomes
- no robustness distribution across seed, slot, lineup, map, player count, or
  enabled-system conditions
- no material-context comparison or classifier version
- no structured AI decision trace, legal-candidate set, reason code, fallback
  count, no-action reason, or illegal-proposal counter
- current mutation/mycovariant recommendations use heuristic confidence weights,
  normal-approximation rate widths, and observational win-lift. They are useful
  diagnostics but are not causal strategy-strength or promotion gates.
- current player summary aggregates by strategy and reports raw win percentage
  and raw cell counts only; cross-player-count comparisons would be misleading.

## 11. Phase 2 Slice Order

Phase 2 should proceed in these independent commits:

1. **P2-A — Manifest domain model and validation:** Add a versioned input/resolved
   model in Simulation, strict validation, 100-game ceiling, and JSON fixtures.
   Initially translate current CLI configuration into the model without changing
   simulation behavior.
2. **P2-B — Complete resolved evidence:** Record all toggles, Adaptations,
   positions/pools, blocked geometry fingerprint, exact lineup, code/balance/
   strategy fingerprints, and explicit seed schedule.
3. **P2-C — Deterministic random seams:** Route AI-relevant unseeded sources
   through declared RNG streams and add replay-equality tests. Keep each behavior
   correction isolated and characterize current behavior first.
4. **P2-D — Replay and diff:** Run a resolved manifest directly, produce semantic
   treatment/control diffs, and reject undeclared differences.
5. **P2-E — Completion/resume protocol:** Unique run identity, checksums, atomic
   completion/failure markers, selective condition resume, and idempotent
   analysis regeneration.
6. **P2-F — Contract proof:** Execute Corpus A and B twice from resolved manifests
   and prove identical per-game results and artifacts, excluding timestamps and
   paths by design.

Characterize the Unity double-invocation issue before architecture migration.
It need not block building the Simulation manifest model, but it blocks claiming
that Simulation is a faithful player-facing AI oracle.

## 12. Phase Exit Assessment

Phase 0 and Phase 1 have enough evidence to proceed to P2-A. No product question
is currently blocking. The immediate implementation boundary is Simulation-only:
introduce the experiment manifest model and validator without changing Core AI
behavior, Unity assets, player-facing pools, or balance.
